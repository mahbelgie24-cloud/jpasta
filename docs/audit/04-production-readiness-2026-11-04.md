# 04 — تدقيق جاهزية الإنتاج (الجولة الثانية، 2026-11-04)

> الفرع: `hardening/elite-upgrade` · خط الأساس: `main@f2cb693` · البيئة: Node 22.20.0،
> PostgreSQL 17 محلي (`127.0.0.1:54330`)، Linux. لا بيانات إنتاج ولا نشر فعلي.

## 1. الملخص التنفيذي

هذه الجولة لم تكتفِ بإعادة تشغيل البوابات: قرأت مسار الأموال والمصادقة والواجهات
والـ Service Worker وCI، ثم أضفت اختبارات تُثبت السلوك قبل الإصلاح. أهم ما وُجد
**عيب أمني حقيقي**: محدد محاولات الدخول كان يعيد تصفير العدّاد عند كل فشل طالما لا
يوجد قفل نشط، فلم يكن القفل التدريجي يُفعَّل إطلاقاً — أي أن الدفاع الوحيد أمام
تخمين PIN سداسي كان معطلاً. أُصلح وأُثبت باختبار تكامل (8 محاولات → قفل).

أُغلقت أيضاً فجوات وظيفية وخصوصية/تجربة: الإدخال اليدوي كان يسجّل كل طلب نقداً
ويجهل طريقة الدفع المختارة، صفحة الحالة كانت تعرض «نقداً عند الاستلام» دائماً،
رابط حالة غير صالح كان يعيد 200 (soft 404)، وأفعال القراءة العامة لم تكن محدودة
بمعدل. أُضيف تشفير النسخ الاحتياطية قبل رفعها، ورُقّيت الاعتماديات (بما فيها
`@lhci/cli@0.16` مع إثبات بوابتي Lighthouse).

## 5. إجراءات المالك قبل الإنتاج

1. إنشاء Hyperdrive + D1 + R2 IDs ووضعها في `wrangler.jsonc`، ثم ضبط الأسرار
   عبر `wrangler secret put` (وفق `docs/DEPLOY.md` §2).
2. إضافة `BACKUP_ENCRYPTION_KEY` كـ GitHub Actions secret (32+ حرفاً) قبل أول نشر.
3. تنفيذ استعادة تجريبية من نسخة إنتاجية على قاعدة scratch (Neon PITR + dump).
4. اعتماد مدة احتفاظ/DSAR وتحديث سياسة الخصوصية بالأرقام.
5. إضافة Web Push keys (اختياري) و`CRON_SECRET` (موصى به) و`VAPID_SUBJECT`.
6. إجراء أسبوع تشغيل متوازٍ قبل التحويل الكامل (Spec §15).

## 6. خلاصة

الكود أصبح أخف ديْناً وأكثر أماناً وقابلية للتحقق: العيب الأمني الحقيقي أُغلق باختبار،
وفجوات الدفع/الحالة/الخصوصية/التشغيل أُصلحت، والبوابات كلها خضراء محلياً.
ما تبقى ليس عيباً في الكود بل موارد إنتاج وقرارات مالك وحدود أدوات خارجية — موثّقة
أعلاه بلا تجميل.
