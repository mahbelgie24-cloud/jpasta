## قواعد التنفيذ المتبعة

1. اختبار يثبت السلوك قبل/مع الإصلاح، ثم تشغيله.
2. أصغر تغيير فعّال، بلا تغيير مخطط أو migration في هذه الجولة (dine-in يستخدم
   enum موجوداً أصلاً).
3. لا تغيير على السلوك المالي المقصود (خصم المخزون عند الإلغاء، tax=0)
   دون قرار مالك.
4. كل commit مستقل برسالة Conventional Commits؛ التراجع `git revert`.
5. بعد كل مرحلة: format/lint/typecheck/test/build، ثم E2E/Lighthouse قبل التسليم.

## المخاطر المتبقية بعد التنفيذ

- لا يمكن الجزم بسلوك الإنتاج الفعلي (Hyperdrive/R2/D1/DO) دون نشر حقيقي.
- أدوات التطوير تحمل ثغرات high (خارج حزمة الإنتاج).
- زمن LCP على الجوال (~4.1s) قريب من البوابة 4.5s ويتأثر بحمل المضيف.
- سيناريوهات الطلب الكبير (>200/يوم أو >200 نشط) تحتاج pagination.
